# Информационная безопасность — кейс 4 «Ситуационный центр»

## 1. Модель угроз

| ID | Угроза | Актив | Вероятность | Ущерб |
| :--- | :--- | :--- | :---: | :---: |
| **U-1** | Подмена показания датчика в канале связи (инъекция ложного `CRITICAL`) | Данные телеметрии | средняя | высокий |
| **U-2** | Несанкционированное удаление или изменение статуса инцидента | Реестр инцидентов | средняя | высокий |
| **U-3** | Доступ сотрудника к чужой технологической зоне без авторизации | Конфигурация и данные участков (`zone_A…C`) | средняя | средний |
| **U-4** | Зависание датчика (`STALE`) не замечено → пропуск реальной аварии | Непрерывность мониторинга микроклимата | высокая | высокий |
| **U-5** | Дублирование инцидентов и алертов от одного физического сбоя | Реестр оповещений и рабочее время инженеров | высокая | средний |
| **U-6** | Перегрузка диспетчера лавиной однотипных алертов (`Alert Fatigue`) | Ситуационная осведомлённость оператора | высокая | высокий |
| **U-7** | Отсутствие следов спорной операции при расследовании аварии | Журнал аудита (доказательная база) | низкая | высокий |

## 2. Меры защиты

| ID | Угроза | Мера защиты | Остаточный риск |
| :--- | :--- | :--- | :---: |
| **U-1** | Подмена телеметрии | Криптографическая подпись каждого пакета `HMAC-SHA256` (секрет известен только датчику и серверу Ingestion) + сверка через `hmac.compare_digest` | низкий |
| **U-2** | Изменение / сокрытие инцидента | Жёсткий граф переходов (запрет `NEW → CLOSED`), ролевая модель RBAC и неизменяемый `append-only` аудит | низкий |
| **U-3** | Доступ к чужой зоне | Изоляция прав доступа RBAC по технологическим зонам (`zone_A`, `zone_B`, `zone_C`) и видимость для инженера только назначенных ему задач | низкий |
| **U-4** | Пропуск `STALE` | Правило **A-4**: автоматическое присвоение статуса `STALE` при пустом значении или молчании датчика > 5 мин с немедленной эскалацией руководителю | низкий |
| **U-5** | Дубли событий | Правило **A-5**: фильтрация повторных пакетов по ключу `(location, indicator)` в скользящем окне 5 минут (300 секунд) | низкий |
| **U-6** | Перегрузка алертами | Двухуровневая градация порогов (`WARNING` до 10%, `CRITICAL` свыше 10%), подавление дублей (**A-5**) и создание автоинцидента (**A-3**) только при 2 `CRITICAL` подряд | низкий |
| **U-7** | Отсутствие аудита | Обязательная автоматическая запись `AuditEvent` из 9 полей (включая `actor`, `at`, `ip`, `from_status`, `to_status`) в `append-only` хранилище при каждой операции | низкий |

## 4. Аудит — структура события

| Поле | Тип | Пример | Назначение |
| :--- | :--- | :--- | :--- |
| **event_id** | string | `evt_0001` | Уникальный идентификатор записи аудита |
| **entity_type** | enum | `incident` | Тип сущности (`incident` / `alert`) |
| **entity_id** | string | `inc_001` | Привязка к конкретному инциденту или оповещению |
| **action** | enum | `status_changed` | Тип операции (`created` / `assigned` / `status_changed` / `closed`) |
| **from_status** | string | `NEW` | Статус объекта до выполнения перехода |
| **to_status** | string | `ASSIGNED` | Статус объекта после выполнения перехода |
| **actor** | string | `e_101` | Идентификатор сотрудника или системного сервиса, выполнившего действие |
| **at** | string (date-time) | `2025-11-01T10:05:00Z` | Точная временная метка события в формате ISO 8601 |
| **ip** | string | `10.0.0.1` | IP-адрес терминала или узла, с которого поступил запрос |

**Регламент хранения журнала аудита:**
* **Режим хранения:** строго `append-only` (только дозапись в конец; модификация и удаление записей технически заблокированы для всех ролей, включая администратора).
* **Срок хранения:** не менее **90 дней** (`≥ 90 суток`).
* **Доступ на чтение:** только **Руководитель** (для разбора инцидентов) и **Администратор** (для контроля целостности).

## 5. Защита данных датчиков

**Запрещённые практики (Что нельзя):**
* **Принимать событие без криптографической подписи:** пакеты без поля `signature` или с неверной подписью немедленно отклоняются с кодом `SENSOR_SIGNATURE_INVALID`.
* **Доверять полю `location` без сверки со справочником:** каждая локация проверяется по `sites.csv`; неизвестные участки (например, `site_99`) блокируются с ошибкой `UNKNOWN_LOCATION`.
* **Хранить секретный ключ HMAC в исходном коде:** хардкод ключей в `.py` файлах или коммит в Git-репозиторий строго запрещены.

**Безопасные практики (Что нужно):**
* **Сверять подпись через `hmac.compare_digest`:** использование функции сравнения за константное время защищает сервер от атак по времени (`timing attacks`).
* **Загружать `SECRET` из переменных окружения:** ключ считывается через `os.environ.get("SENSOR_HMAC_SECRET")` из защищённого окружения сервера.
* **Логировать только метаданные проверки:** в журнал пишутся только `event_id` и результат валидации (`result`), без вывода секретных ключей или сырых токенов.

**Формула расчёта и проверки подписи события:**
```python
payload = f"{event['time']}:{event['location']}:{event['indicator']}:{event['value']}".encode("utf-8")
expected = hmac.new(os.environ["SENSOR_HMAC_SECRET"].encode("utf-8"), payload, hashlib.sha256).hexdigest()
return hmac.compare_digest(event.get("signature", ""), expected)
