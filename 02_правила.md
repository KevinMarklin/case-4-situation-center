# Правила оповещений и жизненного цикла — кейс 4

## 1. Правила оповещений

| ID | Условие | Действие | severity |
| :--- | :--- | :--- | :--- |
| **A-1** | value < norm_min или value > norm_max | Создать оповещение (алерт) | WARNING |
| **A-2** | Отклонение > 10% от нормы | Эскалировать оповещение (алерт) | CRITICAL |
| **A-3** | 2 подряд события CRITICAL по одному датчику в окне 15 мин | Автоматическое создание инцидента (`source=auto`) | CRITICAL |
| **A-4** | Нет данных от датчика > 5 мин (value = "" или невалидный тип) | Перевести в статус `STALE` + эскалация руководителю | STALE |
| **A-5** | Дубль события (тот же `location + indicator` в окне 5 мин) | Дедупликация (игнорировать событие, не создавать второй алерт) | NORMAL |

---

## 2. Формула severity

В системе применяется следующая математическая модель расчета критичности отклонений:

```python
deviation_pct = (value - norm_max) / norm_max * 100.0  # при превышении порога нормы
# или
deviation_pct = (norm_min - value) / norm_min * 100.0  # при недоборе нормы
```

**Пять расчётных веток определения критичности:**

1. **Если `value == ""` или `None` (не число):** `severity = STALE`
2. **Если `norm_min <= value <= norm_max`:** `severity = NORMAL`
3. **Если `0 < deviation_pct <= 5.0`:** `severity = WARNING` (малое отклонение)
4. **Если `5.0 < deviation_pct <= 10.0`:** `severity = WARNING` (умеренное отклонение)
5. **Если `deviation_pct > 10.0`:** `severity = CRITICAL` (аварийное отклонение)

**Обоснование порогов:**
* **До 10% (WARNING):** Превентивный уровень тревоги. Свидетельствует о начале развития технического сбоя (засорение вентиляции, падение мощности обогревателя). Позволяет инженеру устранить проблему до возникновения угрозы для птицы.
* **Свыше 10% (CRITICAL):** Критическое отклонение микроклимата, способное вызвать быстрый падеж поголовья на птицеводческом предприятии или порчу дорогостоящего инкубационного оборудования. Требует немедленной эскалации.
* **Отсутствие данных > 5 мин (STALE):** Опасное состояние «слепой зоны». Так как операторы не видят реальных параметров участка, инцидент приравнивается к критическому для оперативного выезда инженера и проверки связи.

## 3. Жизненный цикл инцидента

Управление инцидентами осуществляется по строгому регламенту переходов состояний. Любые попытки нарушения графа переходов блокируются кодом валидации системы.

### Допустимые переходы

| Из | В | Кто может | Условие / Описание |
| :--- | :--- | :--- | :--- |
| **NEW** | ASSIGNED | диспетчер, руководитель | Назначен ответственный сотрудник (`responsible`), зафиксирован исполнитель. |
| **ASSIGNED** | IN_PROGRESS | инженер, руководитель | Ответственный инженер принял задачу в работу и приступил к устранению. |
| **IN_PROGRESS**| CLOSED | инженер, руководитель | Авария устранена, в систему внесен отчет и причина закрытия. |
| **ASSIGNED** | CLOSED | диспетчер, руководитель | Допускается только с указанием причины `resolution_reason=NO_ACTION` (ложный вызов). |

### Запрещённые переходы

| Из | В | Почему запрещено |
| :--- | :--- | :--- |
| **NEW** | CLOSED | Инцидент обязан пройти цепочку назначения и анализа, чтобы исключить случайное или умышленное сокрытие нерешенных аварий сотрудниками. |
| **CLOSED** | Любой статус | Переоткрывать закрытые инциденты запрещено ради сохранения чистоты метрик SLA. При повторении сбоя создается абсолютно новый инцидент. |
| **NEW** | IN_PROGRESS | Нельзя перескочить шаг фиксации ответственности (`ASSIGNED`), иначе система мониторинга потеряет учет персональной нагрузки персонала. |

## 4. SLA (Соглашение об уровне услуг)

| severity | Время реакции | Время закрытия | Действие при просрочке (Эскалация) |
| :--- | :--- | :--- | :--- |
| **CRITICAL** | 15 мин | 1 ч | Автоматическая эскалация руководителю предприятия, SMS-оповещение. |
| **WARNING** | 1 ч | 4 ч | Напоминание инженеру и диспетчеру в рабочий чат поддержки. |
| **STALE** | 30 мин | 1 ч | Эскалация руководителю смены для отправки инженера на физическую проверку датчика. |

## 5. Роли (RBAC-матрица прав)

Права доступа распределены по принципу наименьших привилегий (Least Privilege) для исключения хаоса и несанкционированных действий сотрудников:

| Действие                          | Диспетчер | Руководитель | Инженер | Администратор |
| :-------------------------------- | :-------: | :----------: | :-----: | :-----------: |
| **Создать инцидент**              |    Да     |      Да      |   Да    |      Нет      |
| **Назначить ответственного**      |    Да     |      Да      |   Нет   |      Нет      |
| **Сменить статус на IN_PROGRESS** |    Нет    |      Да      |   Да    |      Нет      |
| **Закрыть инцидент**              |    Нет    |      Да      |   Да    |      Нет      |
| **Переоткрыть CLOSED**            |    Нет    |      Да      |   Нет   |      Нет      |
| **Изменить справочник участков**  |    Нет    |     Нет      |   Нет   |      Да       |
| **Просмотреть аудит**             |    Нет    |      Да      |   Нет   |      Да       |

## 6. Дедупликация

**Правило:** если в течение 5 минут (300 секунд) поступает несколько событий от одного и того же датчика на одной площадке (одинаковый ключ `location + indicator`) — обрабатывается только первое, остальные отсекаются.

### Техническая реализация в коде (Rules Engine):
```python
if key in seen:
    last_time = seen[key]
    if abs((curr_time - last_time).total_seconds()) < 300:
        return ("DUPLICATE", "IGNORED")

seen[key] = curr_time
```

**Вопрос:** почему это важно? 
**Ответ:** Дедупликация защищает операторов ситуационного центра от так называемой «усталости от алертов» (alert fatigue). При физической поломке датчик начинает генерировать сотни пакетов в минуту. Без фильтрации дублей экран диспетчера мгновенно окажется забит лавиной одинаковых сообщений, из-за чего человек потеряет фокус и гарантированно пропустит критическую аварию на другом производственном участке предприятия.
